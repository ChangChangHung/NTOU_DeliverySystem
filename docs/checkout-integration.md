# 11/25 點餐到接單完整聯測

這次把組員的點餐、購物車和訂單頁接上現有 Flask API，從買家選餐一路測到外送員接單、棄單及完成。遠端實測的兩張訂單、三筆餐點明細最後都是 `completed`，買家與兩位外送員看到的結果也一致。

[完整操作影片](evidence/checkout-flow-20261125/點餐到接單完整測試.mp4)長 148.64 秒，畫面為 1920×1080。這次使用**本機 Vite 前端，透過本機轉送服務連到實際遠端後端**；前端尚未部署成公開網站。最後的核對畫面使用查詢 API，沒有直接登入遠端 MySQL。

## 這次接好的流程

| 頁面 | 已串接的操作 |
| --- | --- |
| `/` 點餐頁 | 讀取餐廳與菜單、加入購物車、增減數量、移除餐點、填備註與送餐地址；重新整理後保留購物車 |
| `/buyer-orders.html` 我的訂單 | 查看這位買家的餐點、地址、外送員與狀態；待接時可取消，外送中可按「已收到餐點」 |
| `/driver.html` 接單大廳 | 查看待接單、接單、查看自己的已接訂單，並前往個別外送訂單頁 |
| `/deliverer-orders.html` 我的外送單 | 只顯示目前示範外送員承接的訂單；外送中可棄單或完成，已完成、已取消的單保留紀錄但不顯示操作按鈕 |

大廳與兩種訂單頁每 15 秒更新，切到背景或離線時暫停。查詢失敗會留下上次清單並顯示錯誤，不會把失敗當成「沒有訂單」；更新成功後才能繼續操作。送出操作時也會鎖住按鈕，避免和查詢重疊。

點餐仍分成兩次寫入：先呼叫 `add_new_order` 建立餐點明細，再呼叫 `add_new_delivery` 儲存送餐地址。兩步都查回確認後，才清空購物車並跳到我的訂單。沿用的頁面設計與取消、棄單、完成按鈕都是組員原有成果，這次主要補 API 串接、資料核對、恢復流程及聯測。

## 這次修正的問題

建單回傳的根層 `timestamp` 曾經比餐點列及查詢結果少一秒。例如根層是 `2026-11-25 04:44:57`，餐點列與查回資料卻是 `04:44:58`；另一筆為 `04:45:47` 與 `04:45:48`，見[時間差紀錄](evidence/checkout-flow-20261125/timestamp-mismatch.json)。最新完整錄影的兩張單沒有出現這個差異，所以前端不能固定加一秒。現在採用 `orders[].timestamp` 的共同值，再查回確認整組 `order_id`、餐點、數量與備註都相符，才建立外送資料。

恢復下單時，處理方式依已知結果區分：

- 餐點已建立、送餐資料未確認：保留原訂單識別，按「繼續完成下單」時只處理這筆 Delivery，不重建 Orders。送出後斷線或收到 `409`，也先查回同單、同地址是否已存在。
- 建單本身逾時、回 `500` 或回應無法核對：保留待確認紀錄，不自動重送。使用者查看我的訂單後，可以歸檔這次本機紀錄、清空購物車再重新選餐；歸檔不會刪除、取消或重送後端訂單。
- 查回同一時間的餐點混入其他 `order_id`：停止建立外送資料，避免把另一筆下單一起當成自己的。

同頁防連點之外，支援 Web Locks 的瀏覽器也會限制同一買家、同一環境的多個分頁同時下單。這只能處理同一瀏覽器的操作，不能保證其他裝置不會在同一秒下單。

訂單頁另外補了 HTTP、JSON、陣列格式、時間、整單狀態與外送員歸屬檢查。Delivery 的合法 JSON `404` 才表示尚未建立；`500` 或 HTML `404` 會顯示錯誤並保留舊清單。後端允許取消已接訂單並保留外送員資料，頁面也已能顯示這種已取消紀錄。完成或棄單的回應不明時，只重新查詢確認，不自動重送操作。

## 在既有環境開啟頁面

先依[本機執行說明](acceptance-runbook.md)準備好後端、Node 和已安裝的前端套件。在專案根目錄執行下列範例，帳號需換成該環境已存在的 ID：

```sh
NTOU_API_TARGET="http://127.0.0.1:5000" \
VITE_BUYER_ID="2" \
VITE_DELIVERER_ID="1" \
VITE_API_SCOPE="local-demo-5000" \
npm --prefix frontend run dev -- --host 127.0.0.1 --port 5173 --strictPort
```

開啟 `http://127.0.0.1:5173/` 點餐；其他三個入口列在上方頁面表格。若要同時展示兩位外送員，可在另一個終端機使用不同的 `VITE_DELIVERER_ID` 與前端 port；連到同一後端時保持相同的 `VITE_API_SCOPE`。

`NTOU_API_TARGET` 由 Vite 設定檔直接讀取 shell 環境變數，不能只寫在前端 `.env` 裡就假設 proxy 會更換目標。`VITE_BUYER_ID` 和 `VITE_DELIVERER_ID` 是示範身分，預設分別為 2 和 1；`VITE_API_SCOPE` 用來區分不同後端環境的本機購物車與待確認紀錄，切換環境時也要更換。

本次遠端錄影另使用 `127.0.0.1:8770` 的專用轉送服務，限制可操作的測試帳號與訂單。錄影 runner 依賴當輪服務與設定，不是 clone 專案後即可一鍵重錄的通用指令。

## 留給後端與團隊確認

| 項目 | 目前限制 |
| --- | --- |
| 建單交易與冪等 | Orders 與 Delivery 分成兩次 API，沒有整張訂單的單一交易或建單冪等識別。前端可以限制補送，但無法替後端保證斷線後只建立一次 |
| 時間與同秒下單 | 根層時間和實際餐點列曾不一致；整單仍用買家加秒級時間識別。需由後端統一時間來源並處理同秒兩次下單 |
| 行鎖與部署版本 | 比對的公開版本 `43b50e7f7fd93278d40c2a21337bac179973f6dd` 缺少本機修正的行鎖；遠端正在執行哪個 commit 尚未確認。本次先後 `409` 不足以證明真正併發時不會互相覆寫 |
| 登入與角色 | 頁面使用示範 ID，JWT、登入身分與角色權限尚未串接；前端只篩選自己的訂單，不能代替後端授權 |
| 收餐與完成規則 | 目前沿用既有 API，買家或外送員都能執行完成操作。收餐碼、雙方確認的順序與條件尚未定義 |
| 取消、刪單與金額 | 可取消／刪除狀態、操作者與紀錄保留規則仍待統一；餐點總額不含外送費，也沒有付款或退款判定 |
| 歷史訂單價格 | Orders 沒有保存下單單價，訂單頁從目前的 `Meals.price` 計算金額，菜單改價會連帶影響舊單顯示。這是原始碼檢查結果，未在共用資料庫改價重現；需要後端保存下單價格 |
