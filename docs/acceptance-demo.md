我接著組員的 `feature/driver-lobby-vue` 分支（`bb80ed4`）做接單整合和測試。大廳、接單 API、時間戳和接單鎖的修正都是原本分支裡的內容；我補上可以直接開啟的接單頁、防連點和錯誤處理，再整理測試結果與報告需要的資料。

## 影片內容

[接單功能 Demo（含資料庫查詢）](evidence/demo-captioned.mp4) 長 52.44 秒，1280 × 900，只有中文字幕、沒有旁白。檔名是「接單功能Demo-含資料庫查詢.mp4」。我用的是本機測試資料，沒有動到組員共用的資料庫。

前 36.44 秒保留 2026-11-14 的接單操作，後面 16 秒是 2026-11-15 補錄的資料庫查詢。我在瀏覽器按下查詢，實際讀取同一份本機 MySQL，沒有重新接單或修改訂單資料。這段是隔天補錄，並非原本接單後連續拍下來的畫面。

影片中，我先讓外送員 #3 透過 API 接走剩下的單，再從還沒更新的畫面按接單，確認會出現 409。這段測的是舊清單；兩人同時接單則另外用 MySQL 測試程式跑了 10 輪，每輪都只有一人成功。我也用新的資料庫連線檢查每筆餐點的狀態，以及最後是哪位外送員接單。

影片第一單是買家 #1、`2030-01-18 20:40:51`，餐點明細 #1、#2 都是 PROCESSING，外送員是 #2。第二單是買家 #4、`2030-02-06 23:42:18`，餐點明細 #3 也是 PROCESSING，外送員是 #3。這些時間是測試資料，不是實際點餐日期。11/14 的結果在[原資料庫紀錄](evidence/browser/demo-database-state.json)；11/15 補錄另外保留了[查詢 SQL](evidence/demo-database-query.sql)、[實際回傳結果](evidence/browser/demo-database-query.json)和[查詢畫面](evidence/browser/demo-database-query.png)。

補錄查的是 `127.0.0.1:3307` 上的 `ntou_acceptance_demo_20261114_b8877ae024`，也就是原影片使用的資料庫。查詢用買家 ID 和時間戳對上 Orders、Delivery，確認同一張單的全部餐點，以及最後由誰接單。

## 報告講稿

我這次接著組員的大廳和接單 API，補上可以直接開啟的接單頁、防連點和錯誤提示。影片先接一張有兩種餐點的單，確認接完後會從清單消失，再重新整理一次。接著測試別人已經接走時會怎麼顯示，再試斷線和恢復連線。影片最後加了隔天補錄的資料庫查詢，可以看到買家 #1 的兩筆餐點都是 #2 接的，買家 #4 的一筆餐點則是 #3 接的。

另外，我用 MySQL 跑了 10 輪兩人同時接單，每輪都只有一人成功，也有查資料庫確認整張單都是由同一位外送員接下。目前還是用測試用的外送員 ID，登入和角色權限還沒接上。
