# 接單測試影片

[新版 Demo：接單流程與例外情況](evidence/demo-accepted-orders-20261115/接單流程與例外情況.mp4)，長 88.32 秒，1920 × 1080，只有中文字幕。這次把兩位外送員的頁面一起錄下來，再切到 MySQL 查詢，直接對照接單前後的結果。

左邊是外送員 #2，右邊是 #3，兩邊都是現有的 `/driver.html`。外面的並排畫面只用來錄影；#2、#3 目前是測試用身分，登入還沒接上。

## 影片順序

| 約略時間 | 操作與結果 |
| --- | --- |
| 0–7 秒 | 兩個頁面都看得到兩張待接訂單。 |
| 7–14 秒 | 先查 MySQL：三筆餐點都是 `PENDING`，還沒有外送員。 |
| 14–26 秒 | #2 接買家 #1 的單，兩種餐點一起出現在「我的已接訂單」。 |
| 26–34 秒 | #3 從尚未更新的頁面接同一張單，收到真正的 `409`，畫面出現紅字。 |
| 34–42 秒 | #3 接買家 #4 的另一張單，自己的清單也有了訂單。 |
| 42–52 秒 | 兩邊重新整理，#2 保留買家 #1 的單，#3 保留買家 #4 的單。 |
| 52–68 秒 | 從接單頁切到資料庫，按重新查詢，再展開 SQL。三筆餐點都是 `PROCESSING`，外送員分別為 #2、#2、#3。 |
| 68–76 秒 | 模擬 #3 暫時連不上後端，重新整理後顯示載入失敗。 |
| 76–88 秒 | 恢復連線再整理，#3 的已接訂單重新出現，資料庫的歸屬也沒有改變。 |

同單衝突這段是 #2 先接、#3 再接，沒有用 API 在畫面外偷偷接走。兩頁同時送出請求則另外放在[自動聯測](evidence/accepted-orders-20261115/browser-results.json)。斷線是錄影腳本暫時攔住 #3 的 API 請求，用來檢查錯誤提示和恢復後的畫面。

## 訂單和查詢紀錄

兩張單都是透過既有下單 API 建立，時間是 `2026-11-15 22:01:25`，直接沿用 API 回傳值。先前影片的 2030 年日期沒有沿用到這一版。

| 買家 | 餐點明細 | 狀態 | 接單外送員 |
| --- | --- | --- | --- |
| #1 | #1、#2 | `PROCESSING` | #2 |
| #4 | #3 | `PROCESSING` | #3 |

接單與查詢都在同一輪完成，使用本機的 `ntou_acceptance_demo_20261115_9d6a752a24`。查詢頁會開新的 MySQL 連線，以 `buyer_id + timestamp` 對上 Orders 與 Delivery。

可以對照[錄影操作與 HTTP 紀錄](evidence/demo-accepted-orders-20261115/demo-events.json)、[接單前的查詢](evidence/demo-accepted-orders-20261115/database-database-before.json)、[接單後的查詢](evidence/demo-accepted-orders-20261115/database-database-after.json)和[恢復連線後的查詢](evidence/demo-accepted-orders-20261115/database-connection-restored.json)。[各自的已接清單](evidence/demo-accepted-orders-20261115/06-both-own-orders.jpg)、[紅字提示](evidence/demo-accepted-orders-20261115/04-real-409.jpg)也有留截圖。

## 報告時可以這樣說

我接著組員的大廳和接單 API，補上接單後的清單和錯誤處理。影片先讓 #2 接一張有兩種餐點的單，再從 #3 還沒更新的頁面接同一張，這時會出現紅字，不能重複接走。#3 改接另一張後，兩邊都能在自己的已接清單看到訂單，重新整理也還在。最後我切到資料庫查詢，確認餐點狀態和外送員 ID 都對得上，也測了連線中斷再恢復。目前使用測試身分和下單 API，登入與買家點餐頁尚未串接。
