# 海大餐飲外送系統：點餐與外送流程整合

盧益甫｜Iteration 2 整合紀錄

我接著組員的接單大廳、點餐與訂單頁往下整合。現在可以從選餐、購物車與地址下單，再進入接單大廳。買家可以追蹤訂單和確認收餐；外送員則能查看、棄單或完成自己接下的訂單。頁面保留組員原有設計，這次補上現有 API 串接、資料核對與錯誤恢復。

## 11/25：點餐到接單完整流程

[完整測試影片](docs/evidence/checkout-flow-20261125/點餐到接單完整測試.mp4)長 148.64 秒。這輪用本機 Vite 前端連到實際遠端後端，買家 #20 建立兩張單，分別由 #21、#22 承接；測過舊卡片重複接單的 `409`、棄單再接回、外送員完成及買家確認收餐。最後查詢的三筆餐點明細都是 `completed`，兩邊頁面也會定時更新。

前端模擬回歸 **20/20**、接單大廳輪詢測試 **14/14**、typecheck 與 build 都通過。原有資料的 API 可見欄位前後比對一致。實際操作、模擬錯誤和本機試跑各自的範圍，見[完整聯測紀錄](docs/checkout-integration.md)。

這次前端仍跑在 localhost，尚未部署成公開網站；影片的 `409` 是先後重複接單，不能代表遠端同時競爭測試。JWT、角色授權、收餐碼與雙方確認規則還沒串接。

## 11/23：接單大廳自動更新

接單大廳現在每 15 秒會重新查詢，待接清單和「我的已接訂單」都會一起更新，不用一直按重新整理。更新時原本的卡片會留著；有人接走訂單，下一輪就會從待接清單移除。

這次接著 `main`（`126b9cc`）修改，沿用組員已經合併的前後端。本機測試的結果、截圖和重跑方式放在[定時更新紀錄](docs/acceptance-auto-refresh.md)。

我用 MySQL 跑了 10 輪兩人同時搶同一張單的測試，每輪都只有一人接成功，另一人收到 `409`，不會把同一張單接走兩次。另外也用一份程式副本拿掉接單鎖，確認測試能抓出重複接單的問題。

## 怎麼開啟頁面

啟動後，`/` 是點餐頁，`/buyer-orders.html` 是我的訂單，`/driver.html` 是接單大廳，`/deliverer-orders.html` 是我的外送單。既有環境的啟動指令與 `NTOU_API_TARGET`、示範帳號設定見[本次串接說明](docs/checkout-integration.md#在既有環境開啟頁面)；本機 MySQL、Python 與前端套件準備則沿用[啟動說明](docs/acceptance-runbook.md)。

目前仍使用示範帳號：買家由 `VITE_BUYER_ID` 指定，外送員由 `VITE_DELIVERER_ID` 指定。點餐與訂單流程已串接，登入身分及外送員權限仍待後端整合。
